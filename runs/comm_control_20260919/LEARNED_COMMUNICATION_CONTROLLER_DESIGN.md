## 〇、六个必答问题的直接回答

1. **控制哪个通道。** 搜索端→救援队的 `CommRelay` 上行（链路 A）的任务视图发射：
   何时首发、是否再供、再供间隔。不改载荷字段，不改接收端合并规则，不碰机器人→机器人 gossip。
2. **相对固定周期与事件规则的潜在价值在哪。** 不在无约束完成率（规则已打满 68/68），
   而在两处可量化差距：**(a) 同完成率下的通信成本**——达到 5.67 目标/episode 的最省规则
   用 128 包/episode，但付出 120.6 个"任务活动却无人知晓"步；在 61 包预算下最好规则只有 5.58；
   **(b) 有损/受限信道下不失守**——丢包率 0.3 时"只发一次"跌到 4.25 目标/episode，
   固定周期重供恢复 5.50 但要 134 包。学习控制器的可声称收益是**在给定包预算内更接近 5.67 上界**，
   不是"提高完成率"。
3. **接收方是否真的受通信策略影响。** 在**隔离设置**下是：同一冻结分配策略，
   接收端信息年龄 70.0 步（只发一次）vs 4.2 步（周期 2），需求误差 14 776 vs 0 步，
   全部由发送策略造成，且切断上行时首次知晓数为 0。在**部署设置**下基本否：
   95.6% 的首次知晓在没有上行时仍由环境视距刷新建立，收窄 `comm_range` 也几乎不改变完成率。
   ⇒ 任何"通信策略有价值"的主张都必须限定为**受控/传感受限/有损信道条件**。
4. **如何区分通信收益与分配策略变化。** 分配端逐项冻结并在每个 episode 运行前断言
   （策略名、参数、发射预算、臂标签含 `+memfix`）；所有条件重放同一份检测流；
   臂标签与 `config_hash` 把条件分开；默认配置经 8-seed 逐记录比对证明与冻结提交一致；
   决策频率混淆项已测量并排除（分配调用次数落在 ±5%，调用最多的条件成绩最差）；
   空闲机器人步与每次调用墙钟一并报告。
5. **是否有充分依据进入训练。有条件地：是，但必须先换一个能区分的场景。**
   当前开发集上"最优规则"与"次优规则"差 0.09 目标/episode（≈12 seed 合计 1 个目标），
   统计功效不足以支撑训练收益的判定；而预算/丢包条件下差距是 1.3–1.4 目标/episode，足以判定。
   因此进入训练的前提是把目标写成**硬包预算下的完成率最大化**，并在预算 61/128 包与丢包 0.3 的
   场景上做（门槛见第六节）。
6. **下一轮最小训练实验怎么做。** 见第一至五节的动作空间、预算标定、划分、回退与成本估计。

## 一、决策过程（MDP）

* **部署节点**：基地区域的发送调度器（与 `TaskRegistry` 同侧）。它不读任何机器人状态，
  也收不到投递回执（无 ACK）。
* **决策步长（关键，避免"少调用模型"与"少发消息"混淆）**：
  每个联合步 `CommRelay.tick()` 调用一次模型，**无论是否发射**；一次调用对当前所有
  "有未说出口的变化"的目标各出一个动作。因此
  `模型调用次数 = 步数 × 有未发变化的目标数`，与 `发射次数` 是两个独立计数，两者都写进转录。
  为降低成本，下一轮把候选集合限制为 `changed_view=True` 的目标（本轮 `_observation` 已经这样标注）。
* **状态特征**（全部为发送节点合法可见，即 `comm_policy.SendItem` 现有字段，无需新增真值）：
  `age_steps`、`since_last_emission_time`、`sent_count`、`pending_event`、`changed_view`、
  `stage_changed`、`requirements_changed`、`members_changed`、`progress_delta`、
  `revision_delta`、`remaining_time`、`has_future_requirements`、当前步在 horizon 中的位置、
  本步剩余预算比例。**不喂** `target_id`、机器人 id、任何接收端状态、任何登记处之外的真值。
  防记忆：特征里不含标识符，测试时按 seed 分块评估（见第五节），并额外跑一次
  "同状态、换 target id"的一致性检查（同一特征向量必须给出同一动作分布）。
* **动作**：每个候选目标一个离散动作 `∈ {send_now, wait_5, wait_20, wait_until_event}`
  （间隔值 = 本轮已标定的周期档位，不新增自由整数）。
  传输层随后按统一顺序裁剪到本步预算——**预算裁剪规则与本轮基线完全相同，学习策略不享有特权**。
* **硬约束（不进奖励）**：
  `max_wait`：非紧急 `age_steps ≥ 10` 时唯一合法动作是 `send_now`；
  紧急（`remaining_time ≤ 25`）时 `age_steps ≥ 3` 即强制。
  这正是本轮 `event_maxwait` 的规则版本，因此模型与规则在同一安全上界下比较；
  终态任务不发射、载荷取发射时刻最新快照、旧未发消息被取代——三条传输规则对所有策略一致。
* **回退策略**：任何一步若模型输出缺失/异常/越界，立即回退到 `event` 规则并计数
  `controller_fallback_steps`（>0 的 episode 必须在报告中单列，不得当作模型行为）。

## 二、目标函数（不做未标定相加）

主目标采用 **ε-约束形式**，避免把"完成奖励"与"消息惩罚"随手相加：

```
maximize   E[on_time]   subject to   packets_per_episode ≤ B
```

* `B` 的取值来自本轮实测（每 episode 包数）：**{34（只发一次的下界）, 61, 128, 245, 455}**，
  预注册主点 `B = 61` 与 `B = 128`（规则基线分别 5.58 与 5.67），压力点配 `delivery_probability=0.7`。
* 训练期实现约束用**拉格朗日项 + 对偶更新**：`r = on_time_credit − λ_t · packets`，
  `λ_{t+1} = clip(λ_t + η (E[packets] − B), 0, λ_max)`；λ 由预算自动标定，
  `λ_max`、`η` 与 λ 轨迹进报告。**若最终要给出加权标量，必须同时报告 ≥3 个 λ 值的权衡曲线**，
  并把"权重来自预算对偶"写明，不宣称任何单一权重是自然选择。
* 上报口径与本轮一致：批次、包、千字节、首知延迟、`age`、需求误差、重规划、调用数、空闲步。
* 判定阈值（预先写定）：
  **通过** = 在冻结独立测试集上，同预算下按时完成率的配对 CI 下界 ≥ 规则基线（不低于），
  且在同完成率下包数配对 CI 上界 < 规则基线；
  **不通过** = 任一 CI 跨阈值的"看似更好"，或依赖放宽 `max_wait`/改预算才成立。

## 三、模型与训练方法

* 策略网络：2 层 MLP（128×128，~17k 参数）或单层 GRU（128，~35k 参数，携带跨步预算状态），
  输出每动作 4 类 logits；动作掩码由 `max_wait` 与预算给出。
* 训练算法：**PPO（clip 0.1，GAE λ=0.95）**，单环境串行 + 12 并行 environment group；
  Critic 允许使用全局真值（CTDE 惯例，仅训练期），Actor 只用第一节特征。
* PILOC、CTDE 权重、联盟规划器、绑定承诺、释放开关、`coordination/allocation_interval` 全程冻结；
  不重训、不改网络输入维度（本轮已确认 observation 维度不变）。

## 四、成本估计（据本轮实测外推）

* 单 episode（1000 步、6 机器人、4–6 目标、CPU 单线程）：隔离条件 **2.3–2.9 s**，
  部署条件 3.5–4.5 s（实测均值 3.1 s，含测量探针）。
* 一次策略评估（12 seeds × 1 条件）≈ 40 s；5 个预算点 × 2 信道条件 × (dev 40 + val 60) seeds
  ≈ **约 2.5 小时 CPU** 全并行 4 进程。
* 训练：20M 环境步 ≈ 20 000 episodes ≈ **17 CPU-小时**（4 并行 ≈ 4.3 h）；
  若改用 GPU 推理不划算（瓶颈是环境步进，不是网络：分配调用 8 ms/次、每 episode 3 100 次 ≈ 25 s，
  与环境 3 s 同量级，训练时须把探针关掉）。
* 预期实验规模：λ 扫描 3 点 × 2 预算 × 2 信道 = 12 次训练 ≈ **3 个工作日 CPU**，
  或压缩为 4 次代表性训练 ≈ 1 个工作日。先跑 1 次 smoke（500 episodes，验证预算与回退计数生效）再开。

## 六、进入训练的门槛（先判定，再训练）

以下三条全部成立才开训；任何一条不成立 → 本轮结论保持"无充分依据"，改做场景/指标修正。

1. **场景可分辨**：在预注册的 `B = 61` 与丢包 0.3 组合下，
   规则基线之间在**同一预算**下的按时完成率配对 CI 不含 0（即确实存在"更省或更稳"的空间）。
   当前开发集上不成立（0.09 目标/episode 差距、12 seed、CI 下界含 0），
   因此必须先跑第 2 条的场景修正版。
2. **信息确有后果**：在受限条件下，把某类消息全部省略会使接收 belief 或任务结局变化
   （本轮已部分成立：`periodic_100` 与丢包条件下成立；无约束条件下不成立）。
   若只在"迟到首知"上成立，则训练目标必须显式包含首知延迟，不能只谈频率。
3. **旁路已被说明并受控**：所有主张限定在 `isolated`/`range_*` 设置，
   且报告部署设置下 95.6% 的替代知晓率——不得把隔离条件下的收益写成真实部署收益。

## 七、下一轮最小实验清单（依序执行）

1. 场景标定：在 dev 块上把 `deadline_tightness` 上界收紧（例如 0.5–1.25）或把 `num_goals` 提到 8–10，
   使 `immediate` 与 `event` 在固定预算下出现可分辨差；**先测规则，不改模型**。
2. 冻结预算与 `max_wait`，把 `conditions.py` 扩成 `budget ∈ {61, 128}` × `channel ∈ {无损, 丢包 0.7}`，
   写入协议文档后再跑。
3. 实现 `LearnedCommController`（4 类动作 + 掩码 + 回退计数），
   单元测试与 `immediate`/`event` 在同一 mock 事件序列上逐字段比对转录口径。
4. 500-episode smoke（预算、回退、λ 轨迹、无 ID 记忆检查）→ 全量训练 →
   验证集选 checkpoint → 冻结测试集一次判定。
5. 报告：同预算下的完成率、包数/字节、首知延迟、`age`、需求误差、重规划与空闲步；
   以及"若把 `max_wait` 放宽 2 倍能省多少包"的敏感性（说明收益来自哪里）。
