# 数据划分审计：哪些 scenario seeds 已经被看过，还有什么能叫"未见"

日期：2026-09-19
对应指令：`COMMUNICATION_NEXT_ROUND.md` §3
机器可读结果：`COMM_DATA_SPLIT_AUDIT.json`（由 `data_split_audit.py --with-configurations` 生成）
本轮分支：`feat/communication-training-stability`

## 1. 审计问题

首轮把 `500000..500399` 登记为"上一轮注册的独立测试集"，并在协议里写下"本轮不触碰"。
指令 §3 要求核查：**一个 seed 块要成为"全项目未使用的最终测试"，前提是全项目没人跑过它。**
总纲 §10 同向：历史开发、已读过的独立测试与分析 seeds 不再作为新版本未见测试集。

"已使用"在本审计里的定义：`runs/**` 下存在该 seed 的任一已执行 episode artefact
（生命周期日志 `rp_*_s<N>.jsonl`、决策轨迹 `tr_*`、通信转录 `ct_*` 或录制流 `s<N>.json`）。
跑过就算看过——一次 episode 的结果会留在人的记忆里，不会因为没写进某篇文档而变干净。

## 2. 方法

只读盘，不跑 episode。两个证据来源，冲突时以 artefact 为准：

1. **artefact 文件名**：本项目每个集成层 episode 都落盘 `*_s<seed>.jsonl`，文件名列表即"实际执行过
   的 seed 全集"，与是否有人写进 manifest 无关；
2. **各轮脚本里声明的 seed 区间**（`range(a, b)`，a ≥ 1000）：这是预注册一侧，即"该轮说它要用什么"。

对重叠块内每个 seed 进一步读取其首条 `run_config`，提取**场景配置指纹**：arm 标签、
`code_commit`、以及被回放流的 `sha256`。同一个 seed 编号在不同配置下不是同一个场景，
必须按配置报告，不能只报编号。

## 3. 结论 A：`500000..500399` 全体已被执行，独立测试资格作废

| 项 | 值 |
| --- | --- |
| 块大小 | 400 seeds |
| 有已执行 episode 的 seeds | **400 / 400** |
| 执行它们的轮次 | `corrected_env_final_20260918`（修正环境 400-seed C/D 独立对比） |
| episode 数 | 每 seed 2 条（C 臂与 D 臂各一） |
| 代码提交 | `f7fea38293540d435b7282450a95c3f9eecabf7e` |
| 步数配置 | 1000 |
| arm 标签 | `coalplan0.25sticky+memfix`（C）、`coalplan0.25sticky+redrel+noself+srccheck+memfix`（D） |
| 每条流的 `sha256` | 逐 seed 唯一，见 JSON `executed_configurations` |

指令 §3 提到"至少存在已知重叠（seed 500168）"。实测重叠不是 1 个而是 **400 个全部**：
该块正是修正环境发布验证用来做 C/D 对比的 400 seeds，其配对差 +0.016125 [0.009250, 0.023959]
就是在这批流上读出来的。

因此：

- 首轮的措辞"上一轮注册的独立测试集 500000..500399"在本轮之后必须理解为
  **"对通信策略调参未使用"**，而不是"全项目未使用"；
- 本轮及其后的通信实验**不得**在该块上跑 episode 并称其为未见测试；
- 首轮/上一轮已在该块上得到的结论（C/D 分配对比）按其原始口径继续有效，不因本审计被撤回——
  它本来就不是通信学习的测试集，是分配控制的独立对比。
- 本审计不追溯"该块的完成率结论是否被看过"这类问题，那属于分配侧；本审计只登记
  "跑过/看过"这一事实，用于通信主线的测试集选择。

## 4. 结论 B：seed 编号与场景内容在本项目是一一对应的

对 `runs/**` 下 1 245 个有录制流的 seed 逐一计算内容哈希：

| 项 | 值 |
| --- | --- |
| 有录制流的 seed | 1 245 |
| 在**多于一种内容**下出现的 seed | **0** |

即同一编号从未在不同场景配置下被重新录制。结论是：**编号重叠即数据重叠**，
不存在"同一个 seed 但换了地图所以是新场景"的辩解空间。这也让 §3 的重叠判定不依赖配置解释。

## 5. 重新预留的最终测试块：`800000..800399`

| 项 | 值 |
| --- | --- |
| 块 | `800000..800399`（400 seeds） |
| 块内已执行 episode | 0 |
| 块内已录制流 | 0 |
| 全项目脚本声明中出现过该区间 | 0 |
| 状态 | **仅登记，本轮不生成、不评估、不查看** |

选择规则写在挑选之前，且与结果无关：**取项目历史上最后一个已用 seed（700071）之上、
100 000 对齐的最低连续 400 块，块内既无 artefact 也无任何 `runs/**/*.py` 声明。**
按此规则 `800000..800399` 是第一个满足条件的块；`900000..900399` 同样干净但更高，
按规则不取（留作再下一轮的候选，如果那时有需要）。
更低的 100 000 对齐块全部不成立：`0..`、`10000..`、`20000..`、`30000..`、`500000..`、
`600000..`、`700000..` 各段都已有执行 artefact。

登记动作 = 本文件 + `COMM_DATA_SPLIT_AUDIT.json` 的 `replacement` 字段。
使用它需要下一轮预注册（冻结策略、规则参数、指标与选择规则之后），且只在预注册之后生成流。

## 7. 限制

- 审计范围是 `runs/**` 的集成层 artefact。PILOC 与 `task_allocation` 自身的训练 seed 索引的是
  地图生成与网络初始化，不是场景身份，未纳入。
- 依赖"每次 episode 都落盘一个带 seed 的文件名"这一约定。该约定自 `joint_eval_20260916` 起成立；
  更早若存在未落盘的临时运行则无法从盘上恢复，只能靠当时的文档，这类情况本审计会漏报而非误报。
- `.gitignore` 排除了原始 jsonl，因此审计只能在**本机磁盘仍然完整**时复现。
  JSON 报告里记录了扫描时间、episode 数与 seed 数，便于将来核对盘是否被清过。
- 新预留块的"清洁"是就本项目历史而言；无法排除外部他人以同一编号做过别的实验，
  这也不在本研究的口径内。
